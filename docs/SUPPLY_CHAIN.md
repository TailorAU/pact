# Source — Supply Chain Security

> **Status:** Procurement-grade baseline. Every artefact Source ships to
> production has a signed image, a published SBOM, and an audit trail of
> dependency-vulnerability decisions.
> **Audience:** Procurement reviewers (QGov, Foxleigh, Nyrstar), security
> researchers, agents needing to verify what they are running against.

---

## Why this exists

A Tier-2 institutional reviewer asks three questions about a vendor's
supply chain:

1. **Can I prove the binary I am running came from your build?** Answered
   by Cosign keyless OIDC signatures in this document's
   §1 Image signing.
2. **Can I see what is inside that binary?** Answered by SPDX SBOMs
   generated by Syft in §2 SBOM publication.
3. **Are you watching for vulnerabilities in your dependency graph?**
   Answered by §3 npm audit gate, §4 Trivy image scanning, and the
   weekly §5 CVE re-scan workflow.

This document is the procurement-facing answer to all three.

## §1 — Image signing (Cosign keyless OIDC)

Every image published to ACR by `.github/workflows/cd-source.yml` is
signed with a [Sigstore Cosign](https://docs.sigstore.dev/cosign/overview/)
keyless signature using the GitHub Actions OIDC token as the trust
anchor. The signature is stored in the registry alongside the image
under the OCI 1.1+ signature spec.

**No long-lived signing key exists.** The trust chain is:

```
GitHub OIDC → Sigstore Fulcio → ephemeral signing cert (10 min lifetime)
                                       ↓
                      cosign sign --yes <image>@<digest>
                                       ↓
                      Signature stored in registry next to image
```

Verification by anyone (no private credentials needed):

```bash
cosign verify \
  tailorprodacr.azurecr.io/source-web:<sha> \
  --certificate-identity-regexp 'https://github.com/TailorAU/tailor-app/.github/workflows/cd-source.yml@.*' \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com
```

The verification asserts:

- The image was built by the `cd-source.yml` workflow in the
  `TailorAU/tailor-app` repository (no tampering, no parallel "private"
  builds).
- The signature was produced by GitHub's OIDC issuer (no rogue
  certificates from outside the trust chain).

**ACR signature support.** Azure Container Registry supports OCI 1.1+
artefact storage (which includes Cosign signatures) by default for ACRs
on the Standard or Premium SKU. If `cosign verify` returns
"no signatures found", the registry has dropped the signature artefact
— file an issue and check the ACR SKU.

**If `cosign verify` fails with "no fulcio trust root":** the local
Cosign client is older than v2.0 and is missing the embedded TUF root.
Upgrade via `brew install cosign` (macOS) or follow the [install guide](https://docs.sigstore.dev/cosign/installation/).

## §2 — SBOM publication (Syft, SPDX format)

After the Docker image is pushed to ACR, the build job runs
[Anchore Syft](https://github.com/anchore/syft) against the image and
emits two artefacts:

| Artefact | Format | Purpose |
|---|---|---|
| `sbom.spdx.json` | [SPDX 2.3](https://spdx.dev/) JSON | Machine-readable component inventory. Standard procurement format. |
| `sbom.syft.json` | Syft native JSON | Higher-fidelity Syft format. Used for downstream tooling (e.g. `grype` re-scans). |

Both SBOMs are uploaded as workflow run artefacts (download via
`gh run download <run-id>`) and retained for 90 days. The SPDX SBOM is
the canonical procurement deliverable.

A reviewer can answer "what is inside Source's production image?" by:

```bash
gh run download <run-id> --repo TailorAU/tailor-app --name sbom-spdx
jq '.packages | length' sbom.spdx.json   # total component count
jq '.packages[] | select(.licenseConcluded != null) | .licenseConcluded' sbom.spdx.json | sort -u
```

For a more formal procurement deliverable, the SBOM can be requested
ad-hoc by emailing `security@tailor.au` referencing the deploy SHA — we
will return a signed SPDX file.

**Why both formats:** SPDX is the procurement standard; Syft native is
the highest-fidelity input for `grype` re-scans (the same tool the
weekly CVE workflow uses).

## §3 — npm audit policy (HIGH+ blocks deploys)

Every production deploy runs `npm audit --audit-level=high` in
`sites/source/` BEFORE the Docker build. Any HIGH or CRITICAL CVE
in the resolved dependency graph fails the build.

This is intentional friction. The policy is:

- **CRITICAL / HIGH (CVSS ≥ 7.0):** blocks deploy. Fix or
  formally allowlist with expiry within the CVSS-7+ 30-day SLA from
  [`SECURITY.md`](SECURITY.md).
- **Moderate / Low:** does not block deploy. Tracked in the weekly
  re-scan output (§5) and addressed opportunistically.

### Allowlist format

Documented exceptions live in
[`.npmaudit-allowlist.json`](../.npmaudit-allowlist.json). Each entry
must have:

- `advisory` — primary GHSA identifier
- `package` — affected package name
- `severity` — `high` or `critical`
- `justification` — why the fix is non-trivial (breaking change, build-only
  transitive, no upstream fix yet)
- `tracking_issue` — link to the GitHub issue that will land the fix
- `added` — date the entry was added (ISO 8601)
- `expires` — date by which the fix must land (ISO 8601). Past-expiry
  entries fail the build.
- `owner` — who is on the hook to clear the entry

**Past-expiry entries cause the build to fail in the same way an
un-allowlisted HIGH CVE does.** The expiry date is a forcing function,
not a snooze button.

## §4 — Trivy image scanning

After every push to ACR, [Aqua Trivy](https://trivy.dev/) scans the
final image for:

- OS-package CVEs (apk packages installed in the alpine base layer)
- Application-language CVEs (Node modules baked into the runtime layer)

**Failure threshold:** any CVE rated `CRITICAL` fails the build. `HIGH`
findings are surfaced in the GitHub run summary as a procurement-readable
markdown table but do not block deploy on their own (npm audit at §3 is
the hard HIGH gate at the dependency layer; Trivy is the second-layer
catch for OS-package CVEs that npm audit cannot see).

The Trivy run summary is attached to every workflow run and visible from
the workflow run page → "Summary" tab.

A reviewer can re-run Trivy against the prod image at any time:

```bash
trivy image \
  tailorprodacr.azurecr.io/source-web:latest \
  --severity HIGH,CRITICAL \
  --format table
```

(Read access to ACR is required for non-public registries; see Knox.)

## §5 — Weekly CVE re-scan

`.github/workflows/source-cve-scan.yml` runs every Monday at 14:00 UTC
(00:00 AEST Tuesday) and re-runs both `npm audit` and `trivy image`
against:

- The latest commit on `main` (for the npm-audit dependency graph)
- The `:latest` tag on `tailorprodacr.azurecr.io/source-web` (for the
  Trivy image scan)

**Why the re-scan exists.** A clean deploy at time T+0 does not stay
clean. New advisories land in the GHSA database every day; an image
that passed the gate yesterday can be vulnerable today even with no
code change on our side.

**On findings.** The workflow:

1. Posts a markdown summary of every HIGH/CRITICAL finding to the run
   summary
2. Files (or updates) a single tracking GitHub issue titled
   `[cve-scan] Source HIGH/CRITICAL findings — <date>` with the
   `security` label and a body listing each advisory and its fix path
3. Does not auto-close the issue on a clean week — Knox closes after
   triage. The continuous existence of an open issue with stale findings
   is the visibility surface.

The workflow can also be run on demand:

```bash
gh workflow run source-cve-scan.yml --ref main \
  --repo TailorAU/tailor-app
```

## §6 — Dependency pin policy

[`.npmrc`](../.npmrc) declares:

```ini
save-exact=true
engine-strict=true
```

Effect:

- **`save-exact=true`** — `npm install <pkg>` writes an exact version
  to package.json (e.g. `"next": "16.1.6"` not `"^16.1.6"`). The
  `package-lock.json` already pins, but with `save-exact` the
  package.json is also a precise dependency record — useful for
  procurement audits and for human review of dependency PRs.
- **`engine-strict=true`** — `npm install` refuses to run if the local
  Node version is outside the `engines` range declared in package.json.
  Catches Node-version drift between local dev and CI early.

**Adding a new dependency.** Run `npm install <pkg>` (no `--save-exact`
needed; `.npmrc` enforces it). Confirm the resulting package.json line
has no caret/tilde prefix.

**Bumping a dependency.** Either run `npm install <pkg>@<version>` (for
a targeted bump) or `npm update <pkg>` (for the latest within the
existing pin range). For HIGH-CVE bumps, prefer a dedicated PR with the
allowlist entry removed in the same commit.

## §7 — Verification — what the gate actually does

A procurement reviewer can verify each of the four controls in under
five minutes:

1. **Image signature:**
   ```bash
   cosign verify tailorprodacr.azurecr.io/source-web:<sha> \
     --certificate-identity-regexp 'https://github.com/TailorAU/tailor-app/.github/workflows/cd-source.yml@.*' \
     --certificate-oidc-issuer https://token.actions.githubusercontent.com
   ```
   Returns the signed claim including the workflow path and run ID.

2. **SBOM:**
   ```bash
   gh run download <run-id> --repo TailorAU/tailor-app --name sbom-spdx
   jq '.packages | length' sbom.spdx.json
   ```
   Returns the component count in the signed image.

3. **npm audit gate:**
   ```bash
   gh run view <run-id> --repo TailorAU/tailor-app --log | grep "npm audit"
   ```
   Confirms the gate ran and exited 0 (or surfaces the allowlist that
   was checked).

4. **Trivy scan:**
   Open `https://github.com/TailorAU/tailor-app/actions/runs/<run-id>`
   and read the Summary tab. The Trivy table is the bottom section.

5. **Weekly re-scan:**
   ```bash
   gh run list --workflow source-cve-scan.yml --repo TailorAU/tailor-app --limit 4
   ```
   Confirms the workflow has been running every Monday and surfaces the
   most recent findings.

If any of the five fails, that is a doctrine failure to investigate —
file an issue at `security@tailor.au`.
